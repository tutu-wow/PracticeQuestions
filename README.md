# 考研政治刷题小程序

> AI 推荐题目 · 章节练习与专项训练 · 随机刷题与每日一练 · 模拟考试与答题卡 · 错题本与收藏夹 · 学习打卡与目标管理 · 题库与组卷维护 · ECharts 数据分析

起因挺实在：准备二战的学长吐槽，政治刷题要么抱着纸质题册一页页翻，要么在几个零散的刷题小程序之间来回切；错题抄在本子上，过两周连自己当初为什么做错都想不起来；等想知道"这个月到底刷了多少、哪个科目最拖后腿"，只能凭感觉估。

这套系统就是冲着这个场景做的：**科目—章节—知识点—题目分层组织，章节练习、专项练习、随机刷题、每日一练共用同一套刷题流程，答错自动沉淀进错题本，模拟考试带答题卡和交卷复盘，打卡与目标把日常坚持记下来，管理端负责题库、试卷和分析看板**。答辩时"错题是怎么沉淀的"和"交卷之后到底落了哪些数据"这两段特别好讲，比单纯罗列增删改查扎实。

## 一、项目简介

考研政治刷题与学习管理系统采用前后端分离架构，由面向学生的 uni-app 微信小程序、面向管理员的 Web 管理端以及 Spring Boot 服务端组成。系统围绕考研政治日常学习场景，提供科目、章节、知识点和题目的分层组织，覆盖章节练习、专项练习、随机刷题、每日一练、模拟考试、错题复习、重点收藏、学习打卡和目标管理等功能；管理员可维护题库与试卷，处理公告和用户反馈，并通过数据看板了解用户、刷题、考试和打卡等业务数据。

## 五、核心实现

### 5.1 双角色账号体系与登录状态

系统区分普通用户和管理员两类角色。普通用户在小程序端完成注册、登录、找回或修改密码、个人资料维护等操作，并进入日常学习流程；管理员通过 Web 管理端进入内容维护与数据分析页面。登录成功后，服务端生成 JWT，前端将登录凭证保存至本地状态与缓存中，后续请求在请求头中携带认证信息；后端拦截器解析当前用户及其角色，为角色菜单、个人数据查询和业务记录归属提供依据。

### 5.2 题库分层管理与练习条件组织

后台以"科目—章节—知识点—题目"的结构维护学习内容。题目可关联所属科目、章节和知识点，并维护单选题、多选题、判断题等题型，难度、来源类型、来源年份、正确答案和解析内容等信息；选项以独立数据维护。管理员可在后台新增、编辑、查询题目及选项，维护科目、章节和知识点，使学生端能够按知识结构加载题目，并为专项筛选和后续分析提供统一的数据基础。

| 学习入口 | 题目组织方式 |
| :--- | :--- |
| 章节练习 | 学生先选择科目与章节，系统按章节条件查询对应题目，适合按知识结构进行系统学习 |
| 专项练习 | 可按题型、难度、来源年份等条件筛选题目，便于围绕薄弱题型或特定来源集中训练 |
| 随机练习 | 前端获取符合条件的题目后打乱顺序，形成随机化的刷题过程 |
| 每日一练 | 根据当天已配置的每日一练及其题目明细进入练习，作为固定频率的学习入口 |

### 5.3 统一刷题、即时判题与学习记录

小程序将不同练习场景汇集到统一的刷题流程中。页面按题型提供不同的作答交互：单选题可直接判题，多选题在选择完成后确认，判断题以"正确、错误"作为固定作答项。完成作答后页面展示正确答案与题目解析，并支持上一题、下一题与答题卡跳转。每次作答会记录用户、题目、练习模式、用户答案、是否正确和用时等信息；答错时同步写入或更新错题记录，形成可回溯的学习行为数据。

四个入口最后都收敛到同一个作答页面，这样做的好处很直接：**判题规则、解析展示、记录写入、错题沉淀只有一份实现**。如果四种练习各写一套作答页，往后改一次判题口径就要改四处，早晚会出现"章节练习判对了、专项练习判错了"这种很难复现的问题。

### 5.4 每日一练、学习目标与打卡进度

管理员可为指定日期创建每日一练，并为其配置题目和题目顺序；小程序首页加载当日配置后，为学生展示"每日一练"入口和题目数量。学生还可在个人学习目标页面设置每日刷题目标。系统以学习打卡记录保存每日刷题数量、正确数量和学习时长，首页据此展示当天刷题数、正确率、连续打卡天数以及科目学习进度，让固定训练、个人目标和日常学习反馈能够关联起来。

打卡这张表是**按天汇总的独立记录**，不是在页面上临时统计。原因很实际：连续打卡天数、历史每日正确率这些数字要按"当天那一刻的情况"保存下来，如果每次都拿练习记录实时重算，题目增删、错题重做都会让历史曲线跟着变，写进论文的趋势图就失去了可比性。

### 5.5 错题本、收藏夹与重点复习

错题本用于记录用户答错的题目、错误次数、最近错误时间和掌握状态。学生可查看错题对应的题干、正确答案与解析，选择单题重做或批量重做，并在掌握后更新状态。收藏夹则用于保存需要重点回顾的题目，支持收藏、取消收藏、查看详情及集合练习。两类数据分别沉淀"做错的题"和"主动标记的题"，为考前复习提供不同维度的入口。

错题记录用的是**"答错即写入或更新"而不是每次追加一条**：同一道题错第 5 次时，需要的是错误次数变得更高、最近错误时间被刷新，而不是错题本里出现 5 条一模一样的题。重复堆积除了把列表撑长，不会带来任何复习价值。

### 5.6 模拟考试、答题卡与结果复盘

后台可维护试卷名称、总分、考试时长、题目数量和发布状态，并提供手动组卷与自动组卷页面；试卷题目明细保留题目分值和排序。学生在小程序端查看已发布试卷后进入考试，页面加载试卷题目，维护当前答题与标记状态，并通过答题卡展示已答、未答和标记题目。交卷时系统生成考试记录和逐题答案记录，保存得分、正确数、错误数、用时及交卷时间；结果页支持按全部、错题和标记题查看作答情况、正确答案与解析，便于完成一次模拟后的复盘。

交卷动作会落**两份数据**：一份是"这场考试考了多少分、用了多久"的考试记录，另一份是"每一道题选了什么"的逐题答案记录。只有前者的话，成绩单上的分数无从解释；只有后者的话，列表页要按试卷逐条聚合才能显示一行成绩。两份一起写，成绩可追溯、明细可复盘。

### 5.7 公告、反馈与内容运营

管理员可维护公告标题、内容、置顶和发布状态；小程序首页展示公告入口，用户可进入公告列表查看已发布内容。用户也可通过反馈页面提交文字和图片，服务端提供文件上传接口用于处理相关资源；后台集中查看反馈并填写回复内容、记录回复时间和处理状态。该设计将学习内容发布与使用反馈纳入同一套运营流程。

### 5.8 多角色协作与 ECharts 数据分析

系统由学生端负责练习、考试和个人学习管理，管理员端负责学习内容与运营数据维护，双方共享同一套后端接口和数据表。管理端首页及分析页面使用 ECharts 呈现统计结果，覆盖用户、刷题、题目、考试、打卡和反馈等维度。

| 分析模块 | 主要数据关注点 |
| :--- | :--- |
| 首页看板 | 用户数、题目数、当日活跃用户、当日刷题量、新增用户和考试参与情况等概览数据 |
| 用户与刷题分析 | 用户注册、活跃趋势、刷题排行榜、学习时长、打卡天数、刷题趋势、科目对比、正确率和练习模式分布 |
| 题目与考试分析 | 题目总量、难易题、正确率、来源分布，以及考试参与人数、成绩分布、平均分、考试趋势和用时分布 |
| 打卡与反馈分析 | 每日打卡趋势、学习时长、正确率，以及反馈数量、回复率、回复时效和每日反馈趋势 |

其中题目分析页把"最难题目 TOP20"和"最易题目 TOP20"直接摆在一起，再叠加题目正确率分布与来源类型分布——**一张页面同时回答"哪些题没人做对"和"哪些题大家都做对"**，管理员据此判断是题目太难、解析没写清，还是知识点本身就需要补录题目。

### 5.9 前后端分离与统一服务支撑

服务端采用 Controller、Service、Mapper、Entity、DTO 等分层组织方式，将题库、练习、考试、打卡、公告和分析模块拆分为独立业务接口。普通结果和分页结果使用统一的数据结构返回，小程序端与管理端分别通过封装后的请求方法调用接口；后端使用 MyBatis-Plus 完成数据访问，并通过 MySQL 持久化业务记录。该架构使移动学习端与后台管理端职责清晰，同时保证题库数据、学习记录和统计结果的一致性。
